What it is

404-GEN is a 3D-generation subnet run by the 404 team. Its current competition, called threejs, asks miners to build a pipeline that reads a prompt image and writes a JavaScript module that constructs the object from Three.js primitives and procedural textures. Rounds run about every three days, and every decision is written to a public git repository. The team is preparing a new phase in which miners submit Python code that may call closed-source OpenAI models through a recording witness, so the operator can replay the work instead of paying for new calls.

How it works

Miners

In the current phase miners publish a public repository with a Docker image that serves an HTTP API on port 10006, built only from open-source, commercially licensed models and pinned dependencies. Each round they reveal a submission on-chain, then generate one Three.js module per published prompt (128 prompts per round) and upload the files to their own CDN. They must lock 100 alpha per hotkey, locked from the coldkey, to take part. In the planned closed-source phase (Competition 3, documented on an unmerged branch) miners instead submit a Python repository with a main.py entry point and a fixed commit, with no Docker image. Each prompt gets a nominal budget of 60 OpenAI calls and 5 US dollars at Standard prices, shared by every attempt.

Validators

Validators download and render each module, then a vision-language model judges pairwise duels per prompt. The margin of a duel is the net score divided by the number of prompts. In the code on the main branch, every miner must first beat the previous round's winner by the win margin to qualify. Qualified miners then face the current leader in reveal order, and a win needs the same margin. A winner is only crowned after audits: the miner's own Docker image is rerun on serverless GPUs, and its regenerated outputs must not be clearly worse than what it submitted. A failed or rejected result is dropped and the next miner takes its place. All round state, matches and audit reports are public in the competition state repository. The planned phase replaces regeneration with replay of recorded model responses plus a separate source audit.

Incentive

Winner stays in: a challenger becomes leader only by beating the sitting leader by the win margin (0.07 in the live config). The weights service gives the current leader the whole miner weight and the remainder, if any, to the subnet owner's uid. The team announced a 0% burn design on 2026-07-28 and removed leader weight decay in code on 2026-07-31. On chain at block 9354737 (2026-10-24 16:47Z), exactly one uid held incentive, 100%, and it was the uid of the leader named in the latest leader entry. That leader took effect on 2026-10-22 after winning round 56; the entry before it dated from 2026-10-07. The subnet's emission split is the chain default (owner 18%, validators 41%, miners 41%, no burn or recycle).

Getting started

  1. Read the miner reference in the main repository: task, output rules, runtime and API specification.
  2. Register a hotkey on subnet 17 and lock 100 alpha from the coldkey for each hotkey you will submit with.
  3. Until the switch: build a Dockerised generator from open-source, commercially licensed models with every dependency pinned, and check it with the reference validator.
  4. Watch the round schedule in the state repository or the round dashboard; reveal your submission on-chain, generate the prompts with the published seed and upload the modules to your CDN.
  5. For the closed-source phase, read the Competition 3 document and miner guide on the witness branch and try the public test witness with a registered hotkey; the team asks miners to wait for the final tests before submitting.

Caveats

  • The main README and the live config file still describe weight decay, but the code removed it in July 2026 and the team announced a 0% burn design; this page follows the code and the announcement. The judge README also quotes a 5% qualification margin while the live config uses 0.07.
  • Everything about the closed-source phase is provisional: 2026-10-26 was a target and was not repeated in later chat, and the miner guide of 2026-10-24 lists the generation window, penalties for overruns, render tolerances, receipt format and sandbox limits as undecided or not yet implemented.
  • The witness client, Pod gateway and the same-block tie-break fix live on unmerged branches; the main branch has not changed since 2026-09-04, so it may not match what miners will run.
  • The chain read is one block (9354737, 2026-10-24 16:47Z). Weights are validator opinions, not payouts. Nine of 11 validators with weight rows pointed at the leader's uid; one points at the owner's uid, and the owner's own validator last set weights about 44 hours before the read, beyond the subnet's activity cutoff of 5,000 blocks.
  • The witness gateway, worker and verifier were read as documentation only, not audited as code, and the round dashboard mirrors the state repository without extra data.
  • Payout and support questions are directed by the team to their own Discord server and are not visible in this channel.
