What it is

Targon is a decentralized confidential AI cloud built by Manifold Labs. Customers rent GPU virtual machines that run inside hardware trusted-execution environments (Intel TDX or AMD SEV-SNP with NVIDIA confidential computing), and the product also lists bare metal, sandboxes and reserved capacity; the site says bare metal is not confidential. Miners supply the hardware by running the team's signed TargonOS image on attested machines. Validators check the hardware through the team's attestation service and set weights from auction targets that the team's backend publishes.

How it works

Miners

Mining means installing TargonOS, a signed operating system image, on a machine that has a TEE enabled in the BIOS (Intel TDX or AMD SEV-SNP), TPM 2.0 and a UEFI boot, then letting it attest to the team's service on every boot. The installer wipes every eligible disk and builds encrypted storage, and it can be run by network boot or from an ISO. Hardware profiles are 8-GPU servers of one SKU: H100, H200, B200, B300 or RTX PRO 6000 Blackwell on Intel, B300 or RTX PRO 6000 Blackwell on AMD (added 10-15), plus CPU-only profiles with 48 threads and 477 GiB of memory; all need 3 TB of storage. The release read was 0.1.0. A separate miner process lists the node addresses and only answers validators that hold a validator permit and at least a minimum stake (default 1,000 alpha); others are refused.

Validators

A validator works in intervals of about 361 blocks (roughly 72 minutes). It fetches each miner's node list every 30 blocks, asks randomly chosen nodes for attestation evidence with a fresh nonce, and sends that evidence to the team's service, which returns the node's auction name, GPU cards and VM id. A VM id seen twice in one interval is rejected, and errors are not retried within the interval. Weights are set at the start of the next interval and skipped if the validator has run for under 180 blocks or found no nodes. The validator runs as a service stack with a local weights helper, on a CPU server with AMD SEV-SNP according to the October docs.

Incentive

The code assumes miners receive 41 percent of the subnet's emission. It turns that into a dollar pool per interval using the TAO price (supplied by the team's backend) and the subnet's moving price. The backend also publishes auctions, each with a target number of cards, a target price, a maximum price per card hour and a minimum cluster size. Each live card earns the auction's pool divided by live cards, capped at the maximum price, and nodes smaller than the minimum cluster size are rejected. If the payouts add up to more than the pool they are scaled down; any remainder goes to a burn distribution the backend supplies and then to a fixed UID. While an auction is under its card target every live card earns up to the maximum price, and more cards push the rate toward the target price. On chain at block 9334306 the weights followed the payout shares of the four miner UIDs and gave about nothing to the remainder UID.

Getting started

  1. Read docs/miner/miner.md and docs/miner/installing-targonos.md in the repo (the docs site mirrors the miner page).
  2. Check that your hardware matches a profile: exactly 8 GPUs of the listed SKU, or a CPU profile with 48 threads and 477 GiB of memory, plus 3 TB of storage, a UEFI machine, TPM 2.0, TDX or SEV-SNP enabled in the BIOS, DHCP and outbound HTTPS.
  3. Install TargonOS by network boot or ISO; this wipes every eligible disk, and the node attests to the team's service on each boot.
  4. Run the miner process with a config naming your node addresses, external address, port 7777 and netuid 4. Validators need a permit and the minimum stake to query it.
  5. Use the stats site to see allocation and estimated earnings, remembering these are estimates and auction targets change.
  6. Validators should start from docs/validator/validator.md (a CPU server with AMD SEV-SNP, database credentials needed) and check chat first, since the hardware advice has changed.

Caveats

  • The team's backend is closed: auction targets, the dollar pool inputs, attestation verification and the burn distribution cannot be audited from the repo. A plain request to the auction endpoint returned a 502 error on 2026-10-21, so live targets were not read, and the stats site is client-rendered.
  • Earnings figures come from the team's stats API and are estimates of allocation, not settled payments. Revenue, buyback and burn statements made in chat on 10-15 were not checked on chain.
  • Validator hardware advice conflicts: chat in August said a TDX CPU server with 8 to 16 cores and about 32 GB of memory, while the October docs say an AMD SEV-SNP server and still use the older VM installer for the validator.
  • Miners asked on 08-27 why emissions had dropped to zero, and no explanation from the team was found.
  • Only four miner UIDs shared the allocation on 10-21, and one of them held about 70 percent. Whether those UIDs are independent operators was not checked.
  • Sandbox capacity was a problem on 10-17 and 10-20, and B300 and B200 capacity was described by the team as fully rented on 08-21 and 10-05. A question about the tower waitlist on 10-17 had no answer in the archive.
  • The site lists a TypeScript SDK as coming soon and the README roadmap lists training, storage and more vendors; none of that was verified.
  • Only about 60 chat messages appeared in the 30 days before 10-21, so activity in the channel is low.
