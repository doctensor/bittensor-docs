What it is

Cascade trains time-series foundation models by making the training data the competition. The forecasting model is fixed and identical for everyone, a small Toto2-4M model trained inside the subnet, and miners submit deterministic code that generates synthetic series for it. Each submission is trained on, scored against the reigning king on private real-world windows, and the best data holds the throne. The team also runs Ephemeris, a forecasting API and agent integration, which it describes as the subnet's inference layer. On 2026-10-23 the team announced a larger mixture-of-experts successor, Cascade v2, with a planned opening date of 2026-10-30; this page describes the competition running today.

How it works

Miners

A miner writes a generator: Python code that streams synthetic series, univariate or up to 32 coupled channels, and is a pure function of its seed, with hash-locked dependencies from an allowlist. No GPU is needed, because the miner pays for their own training run on a rented Lium pod with their own API key. Code is submitted privately to the operator's vault (published only if it is crowned) or deployed publicly and then funded. A hotkey gets one submission, which is used up once it is judged or fails through the miner's own fault.

Validators

The subnet owner's trainer trains the king and every challenger from the same starting checkpoint under the same budget and publishes a signed manifest. Validators check its signature and contract digests, score the checkpoints on the same private, rotating held-out windows (geometric mean of CRPS and MASE across several forecast horizons), run a paired bootstrap, set weights and publish signed receipts that anyone can re-derive with the cascade-audit tool. Validators do not train and a CPU is enough.

Incentive

King of the hill: the king and up to four previous kings share the weights with a halving decay, roughly 52, 26, 13, 6 and 3 percent, and losing challengers earn nothing. A challenger becomes king only if the lower confidence bound of its advantage clears a bar that starts high for a fresh king and decays with tenure (0.4 falling to 0.2 in increment units in the current on-chain setting, not a percentage). After a king holds for about five rounds of tenure, up to three of the reign's best checkpoints become the starting point for later rounds. Legs start when funded and are judged at settlements every 3 hours, while the king is retrained once per 12-hour era. Chain check at block 9342797 (about 2026-10-23 01:00 UTC): 8 validators set weights, all carry the same 5 targets with the same 51.6 percent top share, now on uid 31 (it was uid 76 on 2026-10-22 14:42 UTC), and none goes to uid 0. On 2026-10-21 the five paid uids sat on five different coldkeys, none of them the owner's (not re-tested after the king changed). The emission weights read that day were 18 percent owner, 41 percent validators and 41 percent miners, and miner emission aimed at owner keys is burned rather than paid.

Recent activity

  • 2026-10-23 (#cascade, 2026-10-22 to 2026-10-23) The team announced Cascade v2: a larger mixture-of-experts model targeting 1B+ total parameters, up from the current 4M-parameter model. Lane A is the competition as it is today (submit a generator, train the full model on its data, challenge the king on private rotating tests with public checks on GIFT-Eval, BOOM, TIME and FEV). Lane C, likely next, is application competitions, starting with MarketCast, where miners submit fine-tuning recipes for a separate Timestral base. Lane B, later, is targeted improvements to selected experts. Planned budgets are 100 percent to A if only A runs, 75/25 for A and C, and 50/25/25 for A, B and C, with unpaid shares burned. The repository release is planned for 2026-10-23 and Lane A opens on 2026-10-30 (UTC). The post does not say what happens to the current competition or whether existing hotkeys carry over, and a miner's question about reusing hotkeys had no answer in chat when checked. Getting started

  1. These steps match the docs for the competition running today; v2 is due to ship its own miner CLI and guides, so check the repository after its release. Clone the repository and install it with pip install -e '.[hippius,chain]'. The docs say to use this pinned environment (bittensor 10.5.0), because other versions write on-chain commitments that validators cannot decode.
  2. Copy scripts/example_generator, write your generator, and run cascade verify on it. Optionally fetch the current king with cascade fetch king and compare both with cascade score on your own held-out pool, using --warm-start live.
  3. Register a hotkey on netuid 91 with btcli. One hotkey gets one submission, so keep spare hotkeys for later attempts.
  4. Create a Lium account and set LIUM_API_KEY in the environment. Keep roughly 4 to 6 hours of GPU price on it, since you pay for your own training leg (the docs differ on the exact figure).
  5. Run cascade submit with your generator, the intake URL https://submissions.cascadesub.net, your wallet and a label, then follow it with cascade queue, cascade round and cascade duel --hotkey.

Caveats

  • The documents disagree about the dethrone bar. The README, miner guide and llms.txt describe 1 percent for a fresh king decaying to 0.5 percent. chain.toml and the team's public status feed record a newer bar in increment units, 0.4 decaying to 0.2 over 18,000 blocks, effective from block 9194400 (about 2026-10-02) after a validator vote, and chat agrees with it. Check cascade round for the live value.
  • llms.txt and parts of the README still describe round-based seating (a cap of 8 seats, one GPU type per round, a forecast horizon of 64 only), while the miner guide says rolling intake is live and chain.toml sets no seat cap. llms.txt itself says chain.toml wins. The guides also give different GPU-budget figures (about 4 hours or 6 hours). None of these documents changed between 2026-10-18 and 2026-10-23.
  • Training is run by the subnet owner. Validators verify and score the owner's signed manifest rather than training anything, privately submitted code sits in the operator's vault, and the evaluation windows are private. The owner has used its powers: on 2026-09-28 a decision record removed a king whose generator embedded another miner's private code, and admission rules changed several times in October. Consensus-affecting changes are decided by a 51 percent validator-stake signal, with a typed block as owner override.
  • Weights are identical across all 8 validators that set them, which fits validators copying the verified result of the operator's trainer, so a chain read cannot show independent scoring. In the team's status feed for the 2026-10-15 stake vote, 3 of 10 eligible validators had signed, holding 84.9 percent of the eligible stake (feed numbers).
  • Capacity and reliability have been uneven. Submissions were rejected from 2026-10-13 to 2026-10-15. On 2026-10-22 a shortage of rented GPUs left entries waiting for hours, and a pod-rotation race made one era's king training fail five times; the fix was on an unmerged branch on 2026-10-23, and code written is not proof of what runs in production. The docs say infrastructure failures requeue an entry without spending it, but miners reported lost registration costs after 2026-10-15, which was not verified. No submission was revealed between about 19:28 UTC on 2026-10-22 and 01:36 UTC on 2026-10-23, and the cause is not known.
  • Cascade v2 is an announcement, not a live system. The repository release was planned for 2026-10-23 and had not appeared on the main branch when checked at 01:40 UTC that day, and no public branch mentions it. The announcement does not say what happens to the current competition, existing hotkeys, the sitting king or emissions at the switch. The lane budgets and Lanes B and C are plans, not commitments.
  • Some miner questions had no public answer when checked: why two submissions never dueled the king (asked 2026-10-19, the team said it would check), the 2026-10-21 reports that the evaluation system looked wrong, and how a leg is scored when its rented pod dies mid-evaluation (asked 2026-10-22).
  • Performance and partnership claims, including beating Toto 2.0 4M on two time-series benchmarks with only miner-generated data, the Ephemeris ensemble outperforming individual models and a first place in a trading arena, are team posts on X that were not independently checked. Ephemeris pricing beyond the free signup credits was not read.
  • In chat on 2026-10-15 the team warned miners to ignore anyone offering help by direct message and said it had banned one such account.
  • What was and was not read: chain parameters and weights were read (blocks 9334717 to 9342797), but training runs, the king's scores and the private evaluation windows are operator-run and cannot be checked from outside. The scoring code was not traced file by file, the dashboard app was not parsed, and chat before 2026-10-01 was read only through pinned posts. The roadmap phases in the README are plans, not commitments.
