What it is

SN121 is run by Sundae Bar AI PLC, a London-listed company that sells AI agents and skills to businesses. The subnet works as a rolling series of Challenges, each a business workflow such as market-data comparability or compliance gap analysis. Miners compete to write the best skill for the Challenge, and the best skills can be integrated into the company's commercial platform. The team says the long-term plan is for part of platform revenue to fund buybacks of the subnet token, but this is stated intent and is not visible in code.

How it works

Miners

Register a hotkey on the subnet, create an account on the sundae_bar Lab and connect that registered hotkey as the account's wallet (the form checks the wallet against the subnet's hotkey registry, not coldkey ownership). While a Challenge is open, upload a skill bundle: a SKILL.md of at most 10,000 bytes plus an optional references folder (up to 30 text files, 128,000 characters in total); a single SKILL.md is also accepted. The agent reads a reference file only when SKILL.md names it. There are two submission caps, a daily one (3 per day in the SBC32 brief) and a per-Challenge one (the README says 5 scored per hotkey); the Lab shows the current numbers. A new entry must also differ enough from earlier ones: under 93% similar to other miners and under 97% to the miner's own.

Validators

The team's validator hands each skill to an in-house evaluator (sbevals). A fixed base agent loads the skill, answers every scenario in the Challenge (4 in SBC32, 9 in SBC31), and several graders score the answers: skill use, scenario quality, a holistic rubric and a deterministic novelty check (typical weights 30/30/30/10, set per Challenge). Before scoring, integrity gates read every file and zero any skill that encodes the dataset, mirrors the rubric or addresses the judges. The suite, dataset and rubric are published on each Lab challenge page, each posted score carries a SHA-256 hash, and the evaluator is distributed as a public Docker image. Other validators either child-key to the team's validator or set their own weights.

Incentive

Emissions follow whoever holds first place. The validator puts a fixed share of its weight on the current leader and the rest on UID 0, which is the owner hotkey (the chain setting is Burn, and the README calls the rest burned). The share is a setting: the open-source default is 20%, and the team's live setting was 40%, confirmed on chain between 2026-10-21 and 2026-10-23. The weights go out as one plain setWeights call, rechecked every 30 minutes by default or when standings change. A different miner takes the lead only by beating the leader's best score by a margin (0.01 per the README); inside it the incumbent keeps the lead. Between Challenges, 100% of miner incentive goes to UID 0, as read on chain on 2026-10-22 and 2026-10-24.

Getting started

  1. Read the README (scoring, leader rule, bundle format, FAQ) before asking in chat, and check the Lab or chat for whether a Challenge is open: between Challenges nothing is paid.
  2. Register a hotkey on subnet 121, create a sundae_bar account and connect that registered hotkey as the account wallet, signing the message the form shows. After a re-registration, disconnect the old wallet and connect the new hotkey.
  3. Open the live Challenge brief on the Lab and download its suite files (suite.yaml, dataset, rubric) to see the scenarios and graders; the brief states the step and token budgets and the daily cap.
  4. Write a SKILL.md that teaches a method, put examples and templates in named reference files, and keep each file within the limits.
  5. Upload the folder, a zip or a single SKILL.md on the Lab form, then read the results JSON for grader rationale and gate results.
  6. To run a validator, register a hotkey with a validator permit and use the Docker Compose stack in the sb-validator repo, with model-provider keys.

Caveats

  • Whether a Challenge is open changes within a day. On 2026-10-24 none was being paid on chain, and the chat archive stops on 2026-10-23, so check the Lab and chat for the next brief.
  • The leader's share is a team setting: 20% in the open-source validator default, 40% as read on chain from 2026-10-21 to 2026-10-23. The README says it can change at any time and a brief can override it, so re-read the weights before relying on it.
  • Since SBC30 a close time is not published when a Challenge opens, and the team decides the close after a production-level score and a review. Earlier Challenges had fixed or 'or sooner' close dates. Miners asked for a published close time and a minimum earning window; no team answer was seen.
  • Chain data shows what validators set, not payouts. All 8 validators with a permit carried identical weights at every sample, which fits the README's child-keying, but this read did not check whether the other 7 are child-keys or independent copies.
  • The README says gate internals are not published, but the evaluator ships as a public Docker image that miners can inspect, and no source repository was found. A miner reported that its integrity grader zeroes the SBC32 leader; this is unverified and no team reply was seen.
  • LLM judging is noisy: a miner's local re-run of the SBC32 leader's bundle scored lower than the published score, which is why a 0.01 leadership margin exists. The team says scores are not reproducible to the last digit.
  • Chat disputes about copying and self-mining are unverified allegations, and the team denies them. The suite, per-test rationale, score hashes and weight code are published for audit, but the coordinator API and the gate logic were not read.
  • The buyback plan tied to platform revenue is an intention in the README; no mechanism for it was found in the code, and chat questions about revenue went unanswered in the data read.
