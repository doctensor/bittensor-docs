What it is

Safeguard is meant to be a market for AI safety testing. Miners run adversarial agents that probe a target AI service through a relay that the target's own validator exposes, validators audit the resulting conversations, and other subnets could use the safety score to scale their own miners' rewards. Humans can also label hard cases through a separate human-in-the-loop path. It exists only as a testnet project: the only client described is the team's own demo subnet, and no project activity after early May 2026 appears in the repo, the site or the chat.

How it works

Miners

Miners run a probe agent (the reference one lives in a separate repo, safeguard-miner) that serves a signed POST /probe endpoint and commits its address to chain. Each task names a target relay endpoint and one concern from the validator's catalog. The miner holds a multi-turn adversarial conversation with the target through the validator's relay, so every turn carries a provenance commitment, and returns the transcript with its own severity estimate. It needs a Chutes API key for its attacker and judge models and a publicly reachable address. A second path lets a person review edge cases that the validator routes to the miner's human-review queue.

Validators

The validator is a Django app (vali-django) that the repo says is meant to replace an older validator.py. It finds miners from chain commitments, dispatches probes against registered targets and checks each transcript's provenance; a transcript without valid relay commitments scores zero. It then audits in tiers: a HarmBench-based classifier, a lighter classifier, then an LLM judge, and sends cases where the miner's claim and the audit differ by more than 0.3 to human review. Customer subnets register a signed relay endpoint through an API and can request safety scores.

Incentive

In the Django validator a probe's severity is the audit's score (floored at 0.05) plus up to 0.1 from the miner's own claim plus up to 0.15 for matched detection cues, capped at 1. It is multiplied by a per-concern weight (all 1.0 by default), and a small bonus of at most 0.05 applies when findings are low. Contributions add up per miner over each tempo and weights are set in proportion to them; if no miner earned anything, the whole vector goes to the owner UID, which burns it. A second mechanism splits weight equally among human-review miners, and human labels adjust a probe miner's contribution in the next tempo. The older validator.py uses a different formula (miner claim times audit agreement). Chain weights were not read.

Getting started

  1. Create a wallet and register a hotkey on testnet netuid 444 with btcli (the miner README uses --network test).
  2. Get a Chutes API key; both the reference miner and the validator use it for attack generation and judging.
  3. Clone safeguard-miner, install it with pip install -e ., copy env.example to .env and set the key, wallet, network (test) and netuid (444), then run python miner.py. The miner must be reachable at the address it commits to chain.
  4. To validate, run bash run_validator.sh from the validator repo (defaults: --network test --netuid 444); it also starts the cross-subnet API on port 9090.
  5. For human review, the reference miner has HITL_ENABLED on by default and queues cases at its /ui/hitl page.

Caveats

  • Testnet only. Nothing here describes mainnet emissions or economics. A testnet read on 2026-10-21 shows netuid 444 registered as Safeguard on 2026-04-04 (9 neurons, block 8273099) and netuid 445 as Safeguard Client the same day (6 neurons, block 8273102), which fits the repo's testnet soft launch. Whether any testnet miner or validator is still running is unknown, and no chain weights were read.
  • The repo has been unchanged since 2026-05-07 and the channel's only team posts are from April, so this looks dormant; that is an inference from missing activity, not a statement by the team.
  • The README links or lists DESIGN.md, HITL_DESIGN.md, design_2.md, demo-client/, knowledge/ and a whitepaper, none of which are in the repo at the last commit. The design rationale and the payment model for client subnets (README: future work) cannot be read.
  • Two validators exist in the repo with different scoring: validator.py (the legacy one, multiplying miner claim by audit agreement) and vali-django (audit-led, miner claim worth at most 0.1). Both use the same weight rule. Which one any testnet validator ran is unknown, and code at a commit shows what was written, not what ran.
  • Docs lag code: the validator loop's own header comment still describes the loop as a stub although the file contains dispatch, audit and weight setting.
  • The only client subnet described is the team's own demo (445). No external subnet is shown integrating, and the site's stats and experiments cover the team's own demo targets; the site says its results are research outputs, not a certification. The probe counts and severity percentages on the stats page are undated team figures.
  • Concern weights are uniform by default and the per-concern severity prior is unused (a TODO in the code); how buyers would set weights is not implemented in what was read.
  • The Django validator's README says an earlier validator crash went unnoticed for hours on testnet and a competing hotkey could have captured most emissions; this is the team's statement, undated, and shows the single-validator risk on a small testnet.
  • The ethics document sets design requirements (encrypted transcripts, redacted public reports, protection for human reviewers). Whether they are implemented was not verified.
  • The project site answered over plain HTTP but not over HTTPS from the research machine on 2026-10-21, although the team linked the HTTPS address in chat.
