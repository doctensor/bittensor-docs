What it is

ChronoSeek is a subnet idea for searching inside videos by meaning: given a video and a plain-language description, miners return the time interval where that moment happens. The team ran it on testnet from spring 2026, said in July 2026 that it had bought the mainnet slot SN20, and by late September said it was stepping back. Today the project exists as testnet netuid 298 only, and the chain lists SN20 under a different project (Witness).

How it works

Miners

In the 1.0 design (main branch, testnet) a miner runs a search service that takes a video link and a query and returns timestamp intervals, using a CLIP-style visual model plus a speech-transcript signal that can only boost the score. In the unmerged 2.0 design (dev branch) a miner instead deploys a private retrieval runtime to Chutes, a hosted compute platform, and commits its metadata on chain. Validators accept one permanent valid submission per hotkey.

Validators

Validators build synthetic search tasks from ActivityNet Captions annotations and score each answer by how well its interval overlaps the true one (intersection over union). In the 2.0 code, tasks are hardened: a private clip is cut from the source video, compressed through Vidaio (another subnet) or local ffmpeg, stored on Hippius, and miners see only that clip link plus the query. The default score is 0.75 overlap plus small terms for matching centre, boundaries and length (zero overlap stays zero). Scores are smoothed with a moving average that puts weight 0.1 on the newest result. Requests to miners time out after 150 seconds. Organic API traffic is designed to be served by owner-run copies of the best Chutes runtimes, not by validators forwarding requests to miners.

Incentive

On the main branch, normalized moving-average scores become weights. On the dev branch, weights are rank-based: 75, 20 and 5 percent to the top three miners with a positive score, with ties splitting the slots they span. An optional fixed burn share (default 0 percent) and the fallback when no miner scores above zero both go to UID 0, which is hard-coded. Chain weights were not read, and no mainnet emission claim is made.

Getting started

  1. Clone the repo and check out the dev branch, which holds the v2.0 miner and validator guides (main is the older 1.0 code from 2026-04-22). Python 3.12 or newer and Poetry are required; run poetry install.
  2. Copy .env.example to .env and set your wallet and hotkey names. The guides default to the finney network and netuid 20, so set NETWORK=test and NETUID=298 explicitly for testnet.
  3. Create a Chutes account and API key, copy chronoseek_chute.example.py to chronoseek_chute.py, and deploy the runtime with scripts/deploy_chutes_runtime.py (the miner guide has the exact flags).
  4. Commit the printed Chutes runtime slug on chain using the command the deploy helper suggests. Each hotkey gets one permanent submission, so check the slug first.
  5. Before spending effort, check whether any validator is active: on 2026-10-21 none had set weights for at least 56 days.

Caveats

  • Testnet only. Mainnet netuid 298 does not exist; 298 is the testnet netuid. The test network has 20 neurons and 8 validator permits, no UID has incentive, and every validator's last weight update was 56 to 91 days before 2026-10-21. Nothing here describes mainnet emissions, and test tokens carry no value.
  • The mainnet slot is unclear. The team said it bought SN20 (2026-08-03) and held ownership through conviction (2026-08-19). On chain, the SN20 owner account changed once, around 2026-08-14, and has not changed since, while the identity name changed to Witness around 2026-09-09. The archive does not say whether the team sold, handed over or released the slot, so none of those is claimed.
  • Mainnet SN20 is a different project (Witness, see the SN20 page). Its on-chain identity still lists this project's Discord invite, so people following that link land in the ChronoSeek server.
  • Code is not proof of what ran. The 2.0 design lives on an unmerged dev branch, while main (2026-04-22) describes 1.0. Code and guides default to netuid 20. Whether any validator ran the dev code was not verifiable, and the 2.0 pull request had been open since 2026-07-20 when read.
  • The burn target conflicts: the dev code hard-codes UID 0, while the team said on 2026-08-19 that it burned to UID 240. Which one a live validator used is unknown.
  • Miners in the 2.0 design depend on a Chutes account and credits, and public API traffic is meant to run on owner-controlled Chutes copies, so serving rests on the owner and one outside platform.
  • The project website chronoseek.org gave no response and the MCP endpoint returned HTTP 526 on 2026-10-21 (an origin certificate error), and the site named in the testnet chain identity does not resolve. Claims about the API, demo and MCP are team statements from chat that were not tested.
  • Market-size and commercial claims in docs/BUSINESS_LOGIC.md were not checked.
