What it is

ACORE AI is pitched as a platform for photorealistic 3D virtual agents that speak and show emotion, and its subnet was meant to supply the AI work behind them. The subnet code in the public repo does one thing: validators send a text prompt, miners return a generated 3D object (a .glb file plus a preview image), and a validator-run service scores it from renders. It only ever ran on the Bittensor testnet, no mainnet date was given, and the project has been silent since December 2025.

How it works

Miners

A miner answers a text prompt with a 3D object: a preview image and a .glb mesh, sent inline as base64 or as presigned storage links when the miner enables S3 upload. It appends a fixed style phrase (angled front view, solid background, high quality) to the prompt and passes it to a text-to-3D service of its own on a local port. The repo's bundled generation server is only a stub that waits a few seconds and returns a placeholder, so miners must bring their own model. A miner reports idle or busy status. Its blacklist is meant to reject unregistered callers, but as written the hotkey lookup raises first and the error handler lets the request through (read from the code, not tested). min_compute.yml asks for a 48 GB GPU for miners and 24 GB for validators.

Validators

Each round (default 700 seconds) a validator picks up to 25 serving miners, checks their status, then sends all of them one prompt fetched from a team-run prompt API, with an 87-second answer limit. Responses go to a scoring service the validator operator runs. It renders the mesh from seven angles, rejects images that do not look like a real object, has an LLM (Claude 3 Haiku in the code, using the operator's own key) describe the preview and the renders, and combines text similarity to the prompt, image similarity between preview and renders, and an image-quality model. Separately, the team's own app can send prompts that validators route to a few of the top-incentive miners, returning the best-scored answer; this path is limited to the owner hotkey and does not change scores.

Incentive

Per round the score is 0.25 times prompt-versus-preview similarity, plus 0.5 times prompt-versus-render similarity, plus 0.3 times preview-versus-render similarity, plus 0.1 times image quality; below 0.35 (or below 0.23 on the first term) it counts as zero. Scores are then divided by the round's best and squared, averaged over time with weight 0.1 on the newest round, and when weights are set only averages above 0.4 count, raised to the eighth power, so the top scorers dominate. A speed bonus exists in code but its default weight is 0 (a comment mentions 0.1). Chain weights were not read because the subnet is not on mainnet.

Getting started

  1. Clone the repo, create a Python virtual environment, then install bittensor and the repo (pip install -e .).
  2. Do not register on testnet netuid 405 for ACORE: the testnet chain now shows a different project's registration there (since 2026-03-10), so a new registration would join that subnet, not this one. The steps below describe what the repo's README documented in 2025.
  3. Miners: run your own text-to-3D service on the port set by --generation.endpoint (default 8093), then start neurons/miner.py with --netuid 405 --subtensor.network test.
  4. Validators: run the scoring service in validation/ (needs pytorch3d, CLIP and a Claude API key; validation/README.md is a template stub), then start neurons/validator.py with --netuid 405 --subtensor.network test.
  5. Check state with btcli wallet overview on the test network. No mainnet instructions exist for this subnet.

Caveats

  • Dormant and testnet only. Nothing here describes mainnet emissions or economics. Mainnet netuid 405 was checked on-chain on 2026-10-21 and is not registered. On the testnet chain (block 8273021, 2026-10-21) netuid 405 carries the name verathos and was registered 2026-03-10; that name matches the mainnet subnet 96 project in this index, but whether it is the same team was not checked, and neither the registration owner nor the neurons were examined.
  • Marketing and code differ. The launch post, README and whitepaper talk about text-to-speech, emotion rendering and conversational intelligence; the repo code only generates and scores 3D objects from text prompts and has no speech or emotion scoring. The whitepaper describes the subnet as planned and has no mechanism details.
  • Prompts come from a team-run API (api.acore.app), and the scoring service needs the operator's own Claude API key, so scores depend on a hosted LLM and on a third-party key. The prompt API was not called.
  • The repo is a template fork: README sections for local, staging and mainnet runs and the validation README are leftovers, the wandb defaults are template values, and the bundled generation server is a stub. A working miner or validator needs components that are not in the repo.
  • The team-only organic path (owner hotkey) is not part of scoring, so team app traffic does not show up in the score code.
  • Only the newest commit of the repo was inspected (shallow clone) and GitHub's API was rate-limited, so commit count and any later branches were not checked.
  • The website did not load on 2026-10-21 (no response), so product claims rest on the repo, the whitepaper and chat only.
