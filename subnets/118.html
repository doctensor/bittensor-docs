What it is

Ditto is a subnet that rewards the best harness for giving AI agents persistent memory and tool use. Miners submit a Docker build context that serves a standard HTTP contract, in any language. Validators run each screened image in an isolated sandbox against DittoBench, which tests tool calling and memory recall. The subnet team also sells Ditto, an AI assistant with persistent memory.

How it works

Miners

Build and practice a memory harness locally (the supported reference is a Rust starter kit, but any language works), package its whole Docker build context and upload it with the ditto CLI. Uploading costs an evaluation fee, quoted at 0.1 TAO as of 2026-09-14, and needs a hotkey registered on subnet 118; registering recycles TAO separately from that fee (the docs call it usually larger, but the chain's registration burn read only 0.0005 TAO on 2026-10-22). A Dockerfile RUN instruction must not request an insecure build entitlement (--network=host or --security=insecure): screening rejects it and ditto verify now fails it before the fee. You are rewarded for improving the best artifact, not for serving live inference. A king's source is published 24 hours after its winner emission is confirmed on chain (all 35 listed agents were downloadable on 2026-10-22). On 2026-10-21 the team proposed lengthening that window to 48 hours; the live feed still showed 24 hours. The docs say near-duplicates of another miner's agent are held for human review, while the team said on 2026-10-19 that building on a released king's code is allowed. The repository also carries shadow-only starter kits for coding and router contracts and a unified kit that serves the coding endpoints beside the normal ones; they do not affect the active score or weights.

Validators

A team-operated screener first builds the image, health-checks it and reviews its source under a published policy (v13, rejection conditions I1 to I8: bypassing the model's authority, suppressing its output, tailoring answers to the benchmark and similar). Rulings are tied to exact agent builds, not to miners. Validators then lease scoring jobs from the central platform, run the agent in a sandbox with no outside network, and score it on freshly generated cases whose seed comes from a chain block fixed after the miner commits. Grading is deterministic and judge-free: tool calls are scored on tool name, arguments and order, memory answers by a public per-answer-kind grader, the two halves count equally, and penalty gates scale the composite down for wasteful tool use, inconsistent answers, memory over-calling, cross-user leaks and answers that only work on the original wording (read from the older scorer files; the v13 rules were not read in detail). Every run uses one locked model (openai/gpt-oss-20b through a platform-controlled proxy). Validators then set weights on chain from the shared score ledger. The weight function is a pure fold over the platform's score ledger (one best entry per paying wallet, full-length benchmark runs only), so every validator computes the same vector. A release on 2026-10-22 stopped counting outages of the scorer image or the private dataset against miners. On chain at block 9339641 (2026-10-22), 12 uids held validator permits and 11 of them had set weights; all 11 weight rows put 70% on the owner's uid 0.

Incentive

King of the hill: a challenger takes the crown only after beating the incumbent by the larger of a fixed 0.007 composite margin and a statistical error band, with near misses settled by re-scoring on shared seeds. Entries are compared on an aggregate score (an average over the signed quorum runs plus any accepted confirmation seeds), and the incumbent keeps the crown until the bar is cleared, so the champion is not always the top-ranked entry: at 14:40 UTC on 2026-10-22 the champion was 2nd on the leaderboard (aggregate 0.814) behind a top entry at 0.819. Both carried the same 18-sample aggregate, so the check was run on 15 shared seeds, where the top entry's lead was slightly negative (-0.002) against a required lead of 0.009, and the champion kept the crown. Earlier that day the top entry had only its three quorum runs and the check was unpaired. The champion and the next four miners share the competitive pool by a payout curve that the operator sets on the platform ledger, which validators from version 31 use. The live leaderboard on 2026-10-22 reported 50/20/13/10/7 percent, while the docs and the code's frozen default list 65/14/10/7/4. The subnet owner can set a burn share that scales the whole miner payout down; the public allocation endpoint showed 70% burned on 2026-10-22 (the same revision as on 2026-10-20), and with no eligible miners everything is burned. A token-efficiency adjustment (factor 0.85 to 1.10) exists, but the leaderboard showed it inactive on 2026-10-22 (its cohort listed 6 entries against a minimum setting of 8, and no entry was adjusted). On chain at block 9339641 (2026-10-22) the owner's own uid 0 still held 70.0% of incentive, six uids had incentive and the top five held 97.9%, the same shape as on 2026-10-21 when the five paid miners shared the other 30% in that 50/20/13/10/7 pattern. The subnet's RecycleOrBurn setting reads Burn, and the validator code relies on Subtensor burning miner incentive sent to an owner-associated hotkey, so that 70% is destroyed rather than paid to the owner; the burned amount itself was not measured. Chain weights trail the leaderboard by a tempo or two, so lower ranks on chain can differ briefly from the live board. Dividends were also concentrated: the owner's uid, which holds a validator permit, took 57.4% of them.

Getting started

  1. Clone the monorepo and work in miners/dittobench-starter-kit; copy .env.example to .env and run the seed-user and evaluate commands to practice locally.
  2. Package your build context with the submit command, or run uv run ditto practice for a production-shaped local run.
  3. Check it with ditto verify (no chain calls), then register a hotkey on subnet 118 if needed.
  4. Upload with ditto upload and track it with ditto status; allow a few hours between your first score and visible incentive.

Caveats

  • The docs call Bench v12 the current contract (docs/MINER.md, still saying so in v0.381.2 on 2026-10-22, and adding that v13 will be scored in shadow once scheduled), but the live API on 2026-10-22 reported Bench v13 as active for scoring and emissions. Treat the docs as stale on this point.
  • The burn share is controlled by the owner and changed several times in October (70% since 2026-10-14, and still 70% when last read on 2026-10-22). Check the live allocation view before relying on any payout figure.
  • The docs and the code's frozen default give a 65/14/10/7/4 payout curve, while the live curve on 2026-10-22 was 50/20/13/10/7. The operator sets the live curve on the platform ledger, so it can change without a code release.
  • On the leaderboard API, the composite column is not the figure used for ranking or for the crown decision (the aggregate, called official composite, is). An entry can show a higher composite than the champion and still rank below it.
  • The platform and screener are centrally operated by the team. Miners reported repeated manual-retry and stuck-screening cases in October, and the repository's fail-once policy means a failed screening or scoring attempt waits for an operator to authorise one retry.
  • The screening policy document says v13 is published with activation pending, while live submission records and the team's rulings already refer to policy v13. New repo docs (2026-10-21) describe the private-replay part of v13 as preparation: its results stay report-only until a full verification profile is activated, so the rulings seen in chat rest on the written rules (I1 to I8) and the private-replay check is not yet enforcing.
  • A treasury and service-share mechanism (gamma) is described in the repo as prepared but not activated; the live view showed a 0% service share and no sweep on 2026-10-21. One manual 500-alpha wallet transfer to a GM-credits holding wallet did finalize on chain that day, published with incomplete source attribution; the repo says such a receipt is not an approved source distribution.
  • The chain read covers one block (9339641, 2026-10-22), with an earlier read on 2026-10-21 showing the same shape. It shows who holds incentive and which weights were set, not intent, and the burned amount was not measured.
  • The docs say registering a hotkey recycles more TAO than the 0.1 TAO evaluation fee, but the chain's registration burn read 0.0005 TAO on 2026-10-22; check the live quote that ditto upload shows before budgeting.
  • The team said on 2026-10-19 that a new incentive mechanism is a few weeks away; contest rules may change. The older ditto-platform repository is archived; use the ditto-subnet monorepo.
