What it is

AuditPal is a Bittensor subnet project in which AI agents compete to find vulnerabilities in smart contracts, and a validator scores their findings against known ground truth. The team's later plan, posted 2026-05-26, widens this into an agent-only bug-bounty marketplace with human triage whose labelled data would feed the subnet's benchmarks, plus selling audit agents to enterprises. The subnet has only been run on the test network, and no mainnet date has been given.

How it works

Miners

A miner does not run a service; it points the validator at a public GitHub repository containing an agent.py. The validator clones it, screens the code (the screener bans calls such as os.system, subprocess, eval, exec and pickle), and runs it in a separate Python process on the validator host, handing it the validator's own LLM API key. The agent returns a list of findings, each with a title, vulnerability type, severity, confidence and file and line. Solidity (EVM) contracts are first, and Solana and Move support are listed as coming.

Validators

The validator fetches a challenge and its ground-truth report from team-run backends, queries a random sample of miners, runs their agents and posts per-miner results back to a team backend. In the first repository (V1, last commit 2026-03-09), findings are matched to ground truth by file and line (within 5 lines, with a vulnerability-type fallback) and scored as 0.70 F1, 0.20 severity accuracy and 0.10 metadata quality. A second repository (V2, last commit 2026-04-29) runs each agent in a locked-down Docker container and scores a partial match per finding (file 0.35, vulnerability type 0.45, severity 0.20) with a small penalty per false positive. The team's docs list two benchmarks, the team's own 30-contract Solbench-30 and OpenAI's EVMbench.

Incentive

Three descriptions conflict. The V1 README and a January chat post say the best agent wins 100 percent of the epoch reward; the team's docs say miner emissions are proportional to benchmark rank; and the code in both repositories turns each round's normalised scores into weights with an exponential moving average (default alpha 0.1), with no winner-takes-all logic found. On the testnet no UID holds incentive. Which of the two repositories the testnet validator runs is not stated anywhere that was read.

Getting started

  1. Testnet only, no rewards. Create a testnet wallet, get test TAO and register a hotkey on testnet netuid 310 (the burn read 0.0005 test TAO on 2026-10-21).
  2. Clone the V1 subnet repository and follow its SETUP.md: it asks for 4 or more CPU cores, 8 GB of RAM and 50 GB of disk. The file names an older repository name that GitHub redirects, uses netuid 310 for both its test and main commands, and leaves one register command without a netuid, so set the network and netuid flags yourself.
  3. Write an agent.py that reads the contract tasks and returns findings in the output schema the repository documents, and publish it in a public GitHub repository whose URL starts with https://github.com/.
  4. Start the miner and expect no score until a validator is running: the two testnet validators were idle when read.

Caveats

  • Testnet only. Nothing here describes mainnet participation, emissions or token economics; mainnet has no netuid 310 (chain read 2026-10-21) and the team has given no mainnet date.
  • Testnet chain read 2026-10-21 (block about 8.27 million): 12 neurons, 2 validator permits, zero UIDs with incentive or dividends, and the two validators' last weight updates were about 1.18 million and 2.16 million blocks old, roughly 166 and 303 days at 12 seconds per block. The subnet registered on the testnet on 2025-12-25, before the team's channel claim on 2026-01-12.
  • The three reward descriptions (winner takes all, proportional to rank, moving average of scores) conflict, and the code does not score latency although the README mentions it. Chain weights were not studied beyond the aggregates above.
  • Which repository the testnet validator uses (V1 or V2) was not found. V1 hard-codes team-run backend addresses; V2 reads them from environment variables. In both, challenges, ground truth and results go through team-run services that were not inspected.
  • Security of the design: the validator runs miner-supplied code and passes it its own LLM key. V2's sandbox comments say networking is off, but the code defaults to bridge networking unless SANDBOX_NETWORK is set. Nothing was run.
  • Team site counts (2 validators, 5 miners, 175 audit sessions) match the docs written on 2026-04-30 and may be static; the site's benchmark page on 2026-10-21 showed no runs and 0 percent accuracy, and listed EVMbench as under construction while the docs call it active.
  • The team's channel had hundreds of messages on 2026-03-06, almost all joke replies to a channel-wide ping, so the 291-message total says little about activity.
  • The bounty platform, escrow contracts, docs site and the Agent-as-a-Service plan are team statements or repository contents; none were used or audited.
