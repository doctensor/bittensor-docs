What it is

NIOME is built by Genomes.io, which describes the subnet as a source of privacy-safe synthetic genomic data for drug-response and precision-medicine research. The task live on mainnet since 2026-08-14 asks miners for synthetic CRISPR experiment designs for the HBB gene (the sickle-cell locus), which validators simulate and score. A second code line, V4, turns the subnet into a pharmacogenomic benchmark where miners infer star-allele diplotypes and prescribing actions for synthetic patient cases, and it has run on testnet since 2026-10-06. Netuid 55 was used by an earlier project (Precog) before NIOME.

How it works

Miners

V3 (mainnet): the validator sends every miner the same task and a short-lived upload link (300 seconds). The miner returns a list of CRISPR experiments for the HBB locus: guide RNA, target position, strand, a mutation from an allowed set, Cas9 or Cas12a, and a cell type. Miners must not include predicted outcomes, because validators compute those. V4 (testnet): each miner gets its own bundle of synthetic patient cases, calls the star-allele diplotype for each gene, derives the phenotype and the CPIC prescribing action, and reports a confidence.

Validators

V3: a validator fetches the task from the team's backend, then contacts miners one at a time, giving each a presigned upload link on S3 or Google Drive. About 450 blocks into each 720-block round (roughly 2.4 hours) it downloads the submissions and scores them in five stages: structure and plausibility checks, a simulated cut and repair outcome, a consistency score, and a distribution-fidelity score. The consistency stage trains a random forest with five-fold cross-validation on the validator's own features of each miner's designs (GC content, distance, energy and similar) to predict the simulated outcomes (cut or not, repair path, indel length); the better the outcomes can be predicted, the higher the factor, so it is usually around 0.1 to 0.3. The final score is the weighted score times the consistency factor times the fidelity factor, averaged over three seeds drawn in the validation stage (values from 0 to 1000). Weights are set before block 700. V4 scores diplotype accuracy weighted by rarity, CPIC phenotype and prescribing concordance, a calibration score on confidence, and integrity checks; its docs say the answers, seed and probe map of a round are published after the round closes, and the scoring constants stay private.

Incentive

In the V3 code only the ten best scores get weight, in a fixed split from 30 percent for first place down to 1 percent for tenth. A configured share, called the burn rate, is put as weight on the owner hotkey's uid: the code set it to 99 percent until 2026-10-18 and to 1 percent from then. On chain that hotkey is uid 119, which is the subnet owner's hotkey and also the validator that posts the team's results feed. On 2026-10-23 the chain agreed with the team's feed: eight of nine validators put 29.7 percent on the same top uid, the ten weights equal the top ten of the latest published task times 0.99, and eleven uids had incentive. The subnet-level emission split read on chain is 18 percent to the owner, 41 percent to validators and 41 percent to miners, and the owner-hotkey incentive setting reads Burn. The V4 code uses the same top-ten split with a 2 percent owner share.

Getting started

  1. Read the pinned posts in the subnet channel first: the website says miner and validator documentation is coming soon, and the repo docs describe V3 only.
  2. Miner (V3 guide): Ubuntu 22.04 or similar, Python 3.12, a 16-vCPU machine (the guide also lists a GPU), a reachable axon port. Clone genomesio/subnet-niome, install the requirements, and create a coldkey and hotkey.
  3. Register the hotkey on netuid 55 with btcli (the registration burn was at its minimum of 0.0005 TAO on 2026-10-21) and start neurons/miner.py with --netuid 55 --subtensor.network finney and your axon port.
  4. If your miner never receives tasks, check the miner log for 401 responses and ask in the channel about the receiver check; on 10-19 and 10-20 the team told miners to set require_receiver=False.
  5. Upload each task result to the link in the task within 300 seconds, then check the results feed or the team's W&B project to see whether you were scored.
  6. Validator (V3 guide): about 32 vCPU and 64 GB RAM, Docker, and either S3 or a Google Drive shared drive with a service account for miner uploads. Start it with entrypoint.sh, which also auto-updates from the main branch.

Caveats

  • Chain weights and aggregate incentive were read at blocks around 9,334,100 to 9,334,300 on 2026-10-21 and again at block 9,343,415 (2026-10-23) and match the code and the team feed. Weights are validator opinions, not payouts, and stakes, coldkeys and what the owner uid does with its share were not examined; the incentive setting for the owner hotkey reads Burn.
  • From 10-18 to the evening of 10-21 the feed scored the same 100 miners every round while 256 uids were registered; the cap went away without a code change, and the team's explanation (a storage limit) was not independently tested. Rounds since then score about 200 miners, and typical consistency factors dropped to about 0.1, so scores from the 100-miner period are not comparable.
  • The team's results feed mixes V3 results from one validator (uid 119) and V4-style results from another (uid 35) with no network label. The V4 rows stop at uid 140, and uid 35 sets no weights on mainnet, so they are probably testnet; that is an inference.
  • Claims by participants that scores are a seed-guessing lottery, that the running validator code differs from the repo, and that one operator controls many top uids were not verified here. Checkable facts: the three seeds come from a 1,001-value range, no V3 row in the feed since 10-18 has a consistency factor above about 0.5 (none near 1.0), and the one-per-IP/coldkey rule is not applied in the current code.
  • The consistency factor comes from a random forest fitted to the validator's own features of a miner's designs, then cross-validated; participants argue it rewards seed luck or is fragile (for example a single failing row when every design cuts). The code and the feed were read, but those arguments, including a 10-22 claim about seed knowledge, were not reproduced here.
  • Submissions and weights are keyed by uid, not hotkey. A miner reported on 10-02 that a uid taken over mid-round inherits the previous holder's result, and the team said it would look into it. No fix was seen in the code.
  • Tasks and the leaderboard come from the team's own closed backend, which validators call for the task and report scores to. A single validator publishes the feed; whether the other validators run the same code is unknown.
  • The owner share has appeared as 99 percent, 1 percent and a promised 2 percent in different places: the commit message for the change says 0.1 percent, the value in code is 1 percent, and chain weights show 1 percent. The share is weight on the owner's own validator uid, so it is called a burn only by the team's naming; whether the chain destroys incentive paid to the owner hotkey was not checked.
  • Sources disagree on the current challenge: the website roadmap still lists the HBB CRISPR challenge as active, while team posts relayed on 10-19 say it is complete. The V3 validator guide still tells validators to install Docker for PharmCAT, which the V3 code does not use. The token migration date comes only from team posts.
