What it is

Sentinel is a testnet subnet whose miners run database-query tools inside AMD SEV-SNP confidential VMs, so an AI agent can use a database credential it never sees. Validators check each reply's AMD chip signature offline and compare answers across miners. The team says there are no emissions, and the subnet has been idle on chain since about 2026-10-28.

How it works

Miners

Each miner runs an MCP server in an AMD SEV-SNP confidential VM. A Key Broker releases the database credential only to an enclave that proved it booted an approved image. Every reply is chip-signed and bound to the validator's nonce. There is no model to train.

Validators

Validators send each miner the same query with a fresh nonce and verify the attestation against a pinned AMD root. Scoring code: attestation 40 percent, latency 30, correctness 20, cache hygiene 5, nonce discipline 5. Attestation, hygiene and nonce are gates; correctness is majority agreement and gates only with three or more verified miners.

Incentive

Yuma Consensus with a timelock commit. The team says the testnet has no emissions; the stated reason to run a node is to test the design.

Roles and requirements

Miner Low barrier

Runs a database-query tool (MCP server) in an AMD SEV-SNP confidential VM and answers validator challenges with chip-signed proofs.

  • One tool, a Postgres query tool, read-only by default. No wallet key goes on the VM. Two launch measurements are approved (host firmware changes the value).
  • TESTNET.md (2026-09-24) says mock miners; the 2026-10-04 results doc and README say real enclaves, all run by the team.

Validator Low barrier

Challenges miners with a fresh nonce, verifies the chip attestation offline, scores five axes and sets weights.

  • A laptop does not work: it sleeps, and past the 5,000-block activity cutoff (about 16 h 40 m, guide) a validator is inactive and its miners fall to zero incentive.
  • Weights without a validator permit are rejected; permits go to the top validators by stake. 2 of 64 slots are held (2026-10-31).

Getting started

  1. Read the known-limitation section of docs/mining.md: the proof covers the booted image, not the application.
  2. Clone the repo, make a Python venv, install requirements.txt, and register a hotkey on netuid 554 with btcli on --network test (burn about 0.0005 test TAO).
  3. Miner: run deploy/provision-gcp.sh, read the measurement with scripts/run_miner.py --print-measurement and compare it with TESTNET.md.
  4. Miner: put the hotkey address and measurement in /etc/sentinel/miner.env and start the sentinel-miner service.
  5. Validator: use an always-on Linux box and stake the hotkey for a permit. Dry-run scripts/run_validator.py --once --dry-run, then run it with one --measurement per value in TESTNET.md.

Caveats

  • Testnet only, no mainnet netuid 554 (2026-10-31). The team says there are no emissions, so no price or emission figures are given; the chain's emission flag (off) and a non-zero last-epoch figure were not interpreted.
  • The testnet has been idle since about 2026-10-28 and no team message explains it. Weight vectors were not read.
  • The proof covers the booted image, not the application: on 2026-10-04 a miner with edited code passed attestation and only cross-miner agreement caught it.
  • The correctness check needs three verified miners; the 2026-10-04 test used three on one chip, all the project's. No outside testnet node is established.
  • The 100-percent detection benchmark is the project's own simulation (site: 900 challenges, results doc: 1000) and excludes a miner it calls undetectable.
  • The inherited payment gateway was not examined; the README says no design partners yet. The repo is under an individual's account; the site's claims were not tested.
