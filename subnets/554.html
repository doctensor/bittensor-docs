What it is

Sentinel is a testnet subnet whose miners run database-query tools (over the Model Context Protocol) inside AMD SEV-SNP confidential VMs, so that an AI agent can use a database credential it is never shown. Each miner reply carries a signature from the AMD chip, which validators check offline against AMD's certificate chain, and validators also compare answers across miners. It runs only on the Bittensor testnet, and the team says there are no emissions. The project's own documents state that the proof covers the image that booted but not the application running on top of it.

How it works

Miners

Per the docs, a miner runs an MCP server inside an AMD SEV-SNP confidential VM (a Google Cloud n2d-standard-2 at roughly $30 a month on spot pricing; the team said in chat that testnet miners can be subsidised). A Key Broker releases the customer database credential only to an enclave that has proved it booted an approved image, and the one documented tool is a Postgres query tool that is read-only by default. Each reply is signed by the chip and bound to a fresh nonce chosen by the validator. No wallet key goes on the VM, and the miner by default answers only validators that hold a permit on the subnet. There is no model to train; the team says uptime and response time separate miners.

Validators

A validator finds miners through the metagraph, sends each one the same query with a fresh nonce, verifies each attestation offline against a pinned AMD root, and refuses firmware below a fixed AMD-published floor. It scores five axes, and the weights below are confirmed in the scoring code: attestation 40 percent, latency 30, correctness 20, cache-header hygiene 5 and nonce discipline 5. Attestation, cache hygiene and nonce discipline are gates, so failing one gives a weight of zero. Correctness means agreeing with the majority of other miners, and it only acts as a gate when a round has at least three verified miners. Validators can pin several approved launch measurements, because honest miners on different hosts can measure differently. The validator's default round interval in code is 22 minutes.

Incentive

Weights are set through Yuma Consensus using a timelock commit. Per the docs there are no emissions on this testnet, so nothing here earns and the stated reason to run a node is to evaluate the design and report what breaks. The README also describes slashable TAO collateral for miners, but no collateral or slashing code was found in the repo (see caveats). Individual on-chain weight vectors were not read; only aggregates were.

Recent activity

  • 2026-10-21 (Bittensor testnet chain read) Testnet read: 5 neurons, 2 with validator permits, 3 with non-zero incentive. One validator's last weight update was about 102 blocks old (roughly 20 minutes); another permitted validator's was about 22,900 blocks old (roughly 3 days).
  • 2026-10-09 (GitHub (docs/results.md, last commit 2026-10-17)) The production miner's chip stopped answering and a watchdog rebooted the host, the second such incident after 2026-09-24. A kernel upgrade picked up in the reboot left the launch measurement unchanged, which the project recorded on 2026-10-17 as evidence that the kernel is not covered by the measurement.
  • 2026-10-05 (GitHub (commits and docs/results.md)) New docs say Intel TDX measures more of the boot chain than AMD SEV-SNP does on Google Cloud, and that TDX measurements were reproducible across hosts and regions. This is a feasibility finding for a possible port, not a shipped change.
  • 2026-10-04 (GitHub (docs/results.md)) Three real-hardware miner processes ran on netuid 554, all operated by the project. One with edited query code passed attestation but was zeroed by cross-miner agreement, the first time the correctness gate fired on the live subnet. The docs say this shows the gate working, not independent verification.
  • 2026-09-24 (GitHub (TESTNET.md, measurements.json)) Testnet docs updated: after a miner VM was rebuilt in another zone its launch measurement changed, so validators now accept a set of approved measurements, and the repo lists two.
  • 2026-09-10 (#sentinel) Launch posts in the channel: what the subnet does, miner and validator requirements, a stated limitation (the launch measurement does not cover the application), and that there are no emissions. Asked about mainnet, the team said there is no slot yet, testnet is the focus, and the testnet phase decides the next steps.
  • 2026-08-30 (Bittensor testnet chain read and GitHub) Subnet registered on the Bittensor testnet as netuid 554 (the docs say 2026-08-29; the chain read gives 2026-08-30).

Getting started

  1. Read the known-limitation section of docs/mining.md first. A miner needs an AMD SEV-SNP confidential VM, which the docs price at roughly $30 a month on Google Cloud spot, and the team said testnet miners can be subsidised, so ask in the channel before paying.
  2. Clone the repo, make a Python virtual environment, run pip install -r requirements.txt, and create a hotkey and register it on netuid 554 with btcli on --network test. Registration burn is about 0.0005 testnet TAO.
  3. Miner: run deploy/provision-gcp.sh to create the confidential VM, read its launch measurement with scripts/run_miner.py --print-measurement, and compare it with the values in TESTNET.md. Measurements depend on host firmware, so report a mismatch in the channel rather than treating it as a failure.
  4. Miner: put the hotkey address and the measurement in /etc/sentinel/miner.env on the VM and start the sentinel-miner service. No wallet key belongs on that machine.
  5. Validator: no special hardware is needed. Register a hotkey, take the approved measurement list from TESTNET.md (not from a miner), do a dry run with scripts/run_validator.py --once --dry-run, then run it continuously with one --measurement flag per approved value.

Caveats

  • Testnet only. Netuid 554 does not exist on mainnet at the latest block read (2026-10-21). The team says there are no emissions and testnet tokens have no market value; no price, emission or market figures are given here. The chain's emission flag reads false while a last-epoch alpha emission figure was non-zero, and neither was interpreted.
  • The proof does not cover the application. The project says so and tested it: on 2026-10-04 a miner with edited code passed attestation on real hardware and was caught only by cross-miner agreement, and the 2026-10-09 kernel upgrade did not change the measurement. The docs also say a miner that runs approved code but leaks what it reads, while returning correct rows, would score full marks (the project's own benchmark includes one, labeled undetectable by design).
  • The correctness check is majority-based and needs at least three verified miners. The 2026-10-04 test used three miners on one chip, all run by the project, so it shows the gate firing, not resistance to a coordinated majority. Whether anyone outside the team runs a node on testnet 554 was not established.
  • The headline benchmark (100 rounds against simulated miners in one process, 100 percent of defended attacks caught, no honest miner rejected) is the project's own and excludes that undetectable miner. The site and README say 900 challenges across nine miners while the results doc says 1000 challenges; the difference was not resolved.
  • Docs conflict on real hardware: TESTNET.md (last changed 2026-09-24) says testnet miners still run a mock attestation, while the results doc from 2026-10-04 onward and the README say real-silicon enclaves run on 554. The later documents are treated as current, but no hardware was checked here. The ROADMAP file (2026-09-04) is also behind the README.
  • The README describes slashable TAO collateral and on-chain slashing for failed attestation. A search of the repo's code (outside tests and docs) for collateral and slashing found nothing, and the roadmap places slashing in a later mainnet phase, so treat it as planned, not implemented.
  • The README says validators challenge every 360 blocks (about 72 minutes), while the validator code and validator guide use a 22-minute default round. The code is treated as the reference.
  • The repo also carries an inherited payment gateway (x402 payments and routing of paid inference to another subnet's API) that the README calls live. It was not examined and is not part of how this subnet's miners are scored. The README states there are no design partners yet.
  • The repository sits under an individual's GitHub account. The site could be reached on 2026-10-21 but its claims were not independently tested, and the chat archive for the channel contains only the 2026-09-10 messages.
