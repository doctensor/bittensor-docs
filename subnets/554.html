What it is

Sentinel is a testnet subnet whose miners run database and API tools inside confidential VMs, so an AI agent can use a credential it never sees. Validators check each reply's chip signature offline and compare answers across miners. Since 2026-11-12 the registry lists one Intel TDX image (v5) and the README says TDX; the chain identity still says AMD.

How it works

Miners

Each miner runs an MCP server in an Intel TDX confidential VM booted from the team's signed image, with no shell. A Key Broker releases the credential, a database password or an API key, only to an enclave that proved it booted an approved image. Every reply is chip-signed and bound to the validator's nonce and, from v5, to the TLS key name.

Validators

Validators send each miner the same query with a fresh nonce, about every 22 minutes, and verify the attestation against Intel's root. Scoring code: attestation 40 percent, latency 30, correctness 20, cache hygiene 5, nonce discipline 5. Attestation, hygiene and nonce are gates; correctness is majority agreement and gates only with three or more verified miners.

Incentive

Yuma Consensus with a timelock commit. The team says the testnet has no emissions; the stated reason to run a node is to test the design.

Roles and requirements

Miner High barrier

Runs database and API-key tools (MCP server) in a confidential VM and answers validator challenges with chip-signed proofs.

  • Tools: a Postgres query (read-only by default) and, since 2026-11-09, a web-API request whose key stays in the enclave. No wallet key goes on the VM.
  • TESTNET.md (2026-09-24) says mock miners; results and README say real enclaves, all the team's.

Validator Low barrier

Challenges miners with a fresh nonce, verifies the chip attestation offline, scores five axes and sets weights.

  • A laptop does not work: past the 5,000-block activity cutoff (about 16 h 40 m) a validator is inactive and its miners fall to zero incentive.
  • Weights without a validator permit are rejected; permits go to the top validators by stake. 2 of 64 slots are held (2026-11-13).
  • Since 2026-11-12 measurements.json holds v5 alone.

Getting started

  1. Read docs/mining.md's opening and 'Honest limits' first.
  2. Clone the repo, make a venv, install requirements.txt, and register a hotkey on netuid 554 with btcli on --network test (burn about 0.0005 test TAO).
  3. Miner: docs/mining.md (2026-11-12) boots the team's signed image on a GCP Intel TDX machine; ask the team for image access.
  4. Validator: always-on Linux box, stake the hotkey for a permit. Dry-run scripts/run_validator.py --once --dry-run, then run it with one --measurement per value in measurements.json (one now: v5).

Caveats

  • No emissions per the team (2026-11-13). The owner's validator set no weights from about 2026-10-28 to 11-04, unexplained; both validators' top target is uid 1 (owner's coldkey, no permit).
  • On AMD the proof covers firmware only: a miner with edited code passed on 2026-10-04 and cross-miner agreement caught it. AMD left the registry 2026-11-09; per the team all three miners run v5.
  • Plain HTTP (T25) is closed only on Intel TDX, for an agent that trusts just the customer's CA; the TLS key name is signed only from v5. Validators do not require TLS yet.
  • The correctness check needs three verified miners; the 2026-10-04 test used three on one VM, all the project's.
  • The site dropped its '100 percent detection' claim by 2026-11-08 and now offers TDX pilots, unaudited by its own account; docs/results.md still says an exfiltrator scores 1.0.
  • README (2026-11-12): no design partners, no independent miners; the approved list means images the team signed, and no outsider has rebuilt one. The API-key tool ran only in the team's own test.
