What it is

Tag101 is a subnet for tagging social posts. Validators draw X posts from a team-run database of posts from a published whitelist of accounts (AI-related accounts at launch) and send each one to miners, who return a few short tags such as entities, topics or events. The team plans to sell the resulting tags as structured signals for trend detection, search and research; a first product called SignalFeed was announced on 2026-10-09. There is no fixed correct answer for a post, so rewards come from how a miner's tags compare with the other miners' tags and with the post text.

How it works

Miners

A miner receives an X post from a validator about every 15 minutes (the default task interval in the code) and returns up to 3 short tags (the repo's task limit is 3). The reference miner asks an OpenAI-compatible chat model, gpt-4o-mini by default, for exactly 3 lower-case tags, so a default miner needs an OpenAI key; miners can replace this with their own logic. Stated minimum hardware is 2 CPU cores, 8 GB RAM and no GPU. A miner serves an HTTP endpoint, publishes it on chain and, by default, also announces it to the team's task server. Out of the box a miner accepts calls from any registered hotkey, not only validators, unless the validator-permit option is switched on.

Validators

A validator pulls posts from the team's task server (crawler.tag101.ai by default), sends each post to the miners and scores the answers with the shared reference scorer. Since release 1.1.0 the posts come from a tweet corpus whose digest is pinned to a published hash; release 1.1.1 pins a rebuilt corpus. The scorer puts all tags from all miners on one post into clusters (between 3 and 8), then gives each tag the mean of three scores: signal (how many different miners support its cluster, how close the tag is to the cluster centre, and stability checks), validity (relevance to the post and format, in tiers of 0.3, 0.6 and 1.0) and utility (how well separated and label-like the tag is). A miner's task score sums its best tag per qualifying cluster. Miners that submit an identical tag set are scaled down by a curve that barely bites until roughly 50 miners share the same set. Task scores are averaged over a rolling 24 hour window per UID and turned into weights with a softmax (beta 10). A validator uses other validators' signed scoreboards only if they cover more than half of qualified validator stake; otherwise it uses its own.

Incentive

Rewards follow the validator weights, so a miner earns more when its tags land in clusters that many other miners also reach, sit near the cluster centre and are close to the post text. By design a score depends on what the other miners send. From 2026-07-31 the code sent 90% of each validator's weight to UID 0 (a burn or owner share that community messages described as going to the owner hotkey; not checked on chain). Release 1.1.0 on 2026-10-08 set that share to zero in code. How much the chain currently pays this subnet was not read.

Getting started

  1. Register a hotkey on netuid 101 and install Python 3.12, then create a virtual environment and run pip install -e . in the repo.
  2. Copy deploy/miner.docker.example (or miner.pm2.env.example) to an env file and fill in the wallet, hotkey, axon port and public IP, plus OPENAI_API_KEY (optional OPENAI_BASE_URL and OPENAI_MODEL) if you use the reference miner.
  3. Build the image with python -m tag101.deploy.docker_node build --image tag101:latest, then start a miner with docker_node start --role miner --env-file <file>; the PM2 route is python -m tag101.deploy.pm2_node.
  4. A validator follows the same steps with validator.docker.example and --role validator.
  5. Check that tasks arrive and are answered with the status endpoint linked above, and keep the repo current: the Docker flow auto-updates and the team has shipped breaking releases.

Caveats

  • Chain weights, emissions, stake, the metagraph and who owns which UID were not read. Statements about burn, whales or self-mining in chat are community claims that were not verified; the team has said that it neither encourages whale behavior nor runs the miners that members point at, and that several groups compete.
  • Members complained in October that one group holds well over half of the UIDs (their counts ranged from about 140 to 153) and that this group wins most of the reward, and some called the subnet self-mined. Others replied that open registration and competition apply to everyone. The code confirms that scores depend on other miners' answers and that repeated identical sets are only penalised strongly near 50 copies; whether the scorer measures tag quality is the main open dispute.
  • Score history is stored per UID in the validator code. Members argued in October that a new miner inherits the old occupant's scores; the team said inherited scores help new miners. The code was not tested for this.
  • Tasks, the corpus credentials and the signed announcements all go through a team-run server, so the subnet depends on that server being up. A member reported it not answering HTTP from 2026-07-31, with no reply in chat; it was answering on 2026-10-21.
  • The stock miner accepts task calls from any registered hotkey by default; a miner operator reported on 2026-10-15 being flooded by another miner and asked the team for help, with no reply seen in chat by 2026-10-21.
  • Code at a commit shows what was written, not what each validator runs. Which validators have upgraded to 1.1.x was not checked, and the README does not mention the 15 minute cadence or the 24 hour window.
  • The public site roadmap lists LLM-based scoring, insight tags and an open API as planned, not live. The SignalFeed product was announced in chat; its page was not read.
