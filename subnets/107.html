What it is

Minos rewards miners for tuning the settings of existing DNA variant-calling tools (GATK, DeepVariant and bcftools) so that they find the most real mutations with the fewest false calls. Every 72 minutes the platform builds a new genome sample with hidden synthetic mutations, and validators re-run submitted configurations and score them against the known answers. The team calls the first phase a search of the tools' parameter space, with custom algorithms and a second incentive mechanism (IM2) planned next.

How it works

Miners

Each round miners download a new alignment file, run a variant caller on a CPU machine and submit the tool configuration they used, limited to published parameter ranges. A hash of the config must be committed on chain first. Miners can try the scoring without registering using the demo and practice modes of the miner script. Top submissions use a different config each round according to the team, so there is no single winning setting, and several miners say the search is expensive in compute.

Validators

Validators fetch tasks and truth data from a team-run platform service, re-run miner configs in Docker and score the resulting variant file with the hap.py benchmarking tool through the project's scoring code. They do not all score everyone: the platform gives each validator a primary range of miners by stake rank (neighbouring validators overlap by about a fifth as a cross-check) and a secondary list to work through until shortly before the deadline. After the window closes, each validator pulls its peers' scores for the miners it did not cover, then sets weights, and it skips weight-setting for the round if that fetch fails. The scoring version and reward shares are read from a public network-config endpoint that the team controls, and a validator will not set weights without it. The team also publishes a block-hash task selector and releases the truth files after each round so miners can check the draw and re-score locally. On chain on 2026-10-21 there were 8 validator permits, and the validator on the owner's own coldkey held about two thirds of the stake counted across the subnet's hotkeys, so its weights carry the most.

Incentive

The live network configuration on 2026-10-21 gives the top-scoring miner of the current round 80 percent of weight and shares the other 20 percent among the next 19 ranks with a 0.9 geometric decay, with no burn. The chain matched this: all 8 validators put 80 percent on their top miner, the next ranks received about 2.3, 2.1, 1.9 and 1.7 percent, and the owner's slot received no weight. The winner changes from round to round: the top miner and the validators' top choice differed across three reads about 400 blocks apart. Only one hotkey per coldkey can be rewarded (the 20 paid uids sat on 20 different coldkeys), and a miner must have scored in at least 5 of the last 20 rounds. Equal scores are broken by earliest submission. Scoring is version 2: 70 percent core accuracy and 30 percent germline accuracy, with a plausibility gate. The small shares for ranks 2 to 20 were added in May and June 2026, according to the team, to keep good miners from being deregistered. The code defaults and the August notice still say 90 percent for the winner, but validators do not use them.

Getting started

  1. Clone minos_subnet, run bash install.sh and read the README; a CPU machine with 4 or more cores and Docker is enough, and the repository pins Bittensor 10.3.1. The repository docs are newer than the Mintlify docs site, so prefer them.
  2. Try bash start-miner.sh --demo, which needs no wallet and prints the exact score a validator would give a fixed sample, then --practice to test configs on the answered chromosome 18 to 22 samples.
  3. Read the live network config and parameter-ranges endpoints before tuning, because scoring version, rewards and allowed ranges change there first.
  4. When ready, run bash start-miner.sh, create or select a wallet and register a hotkey on subnet 107; expect several rounds before you are eligible for rewards (5 scored rounds out of the last 20).

Caveats

  • Everything that sets rewards is controlled through a team-run platform and its network-config endpoint, and the tasks, truth data, assignments and the peer scores that fill each validator's gaps come from the same platform. The team has added hashes, a block-hash task selector and post-round truth files so that miners can check parts of the process, but it will not publish validator logs.
  • Share history: the August notice and the code defaults say 90 percent for the winner, while the live configuration and the chain on 2026-10-21 show 80 percent. No announcement of that change was found.
  • Accusations of copying, multi-UID occupation and self-mining are unresolved. The team says about one round in three is a tie and that it has no evidence of copying; some miners disagree. On chain, 96 coldkeys held the 100 slots and only 3 held more than one, but one rewarded hotkey per coldkey would push any fleet onto separate coldkeys, so this settles nothing. Configs are committed as hashes on chain; the configs themselves stay on the platform.
  • The repository's architecture doc contradicts itself about when validators can see the truth file (held back while submissions are open in one place, available to validators while open in a table). The reference validator code only fetches truth for rounds already in the scoring phase, which fits the first reading. The platform's own enforcement is closed code.
  • The Mintlify docs site is out of date: it predates commit-reveal, subset scoring and scoring v2, and still has a FreeBayes guide although FreeBayes was retired in May 2026.
  • Config search is compute-hungry and, per the team, leading entries use configs fitted to each round, so newcomers face a tuning and cost barrier.
  • IM2, custom algorithms, the macOS app and the commercial pilots mentioned by the owner are chat statements only; no public IM2 code, release date or revenue figures were found. The paid-resubmission fee announced for September was still disabled on 2026-10-21.
  • The chain's weights version key is 20, which by the repository's version-packing rule corresponds to release 0.2.0, while the repository is at 0.3.0; the minimum has not been raised to the current release.
