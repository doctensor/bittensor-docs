What it is

EveryFrame (SN117) is the serving layer behind EveryFrame Studio, a consumer AI video and image studio that puts third-party models from vendors such as MiniMax, Seedance, Veo and Kling behind one credit balance. Miners do not run models themselves: they bring their own provider API keys and run a team-approved worker inside an Intel TDX confidential VM on Phala Cloud, which calls the provider and signs a receipt for the output. The team's own docs call this distributed serving, not decentralized GPU inference. A new team took over the slot from an earlier project on 2026-09-21.

How it works

Miners

Register a hotkey on SN117, fund a Phala Cloud account and at least one provider account (the docs list ten providers, among them fal, OpenRouter, MiniMax, Replicate, Google, Runway, Luma and ElevenLabs), and deploy the approved worker with the everycli command-line tool; no GPU is needed. Miners post a discount for each model contract they offer, and the team's coordinator assigns jobs from those offers, one active job per miner. The worker calls the contract's fixed provider endpoint, downloads and hashes the output inside the TEE and signs a receipt. Hosting and provider usage cost the miner money, and the docs say rewards are not guaranteed. The team said on 2026-10-12 that GPU providers cannot join yet.

Validators

The team's operator side finalizes one signed accounting report per accounting epoch (361 blocks) that lists approved miner work in US dollars, and publishes it as JSON on a public feed. Independent validators (repo everyframe-validator, run as a Docker image) verify the signature and chain provenance, recompute the weights locally and submit them with their own hotkey. They do not re-run models or check customer payments, so the trust model is the operator's accounting. A job counts only after the coordinator verifies the TEE receipt, decodes the media in a no-network sandbox and an operator approves it, and only if it is organic and reward-eligible. The TEE shows which worker image ran and that the receipt was signed in-session; it does not show that the provider ran the model or how good the output is. Since validator v0.4.0 (2026-10-21) each chain epoch gets at most one submission, and later reports are processed even when an earlier one is missing; with no report at all the validator falls back to a burn-only plan after a grace period.

Incentive

Policy epoch-value-cap-burn-v2. Each epoch the pool in dollars is the alpha emission times the miner share times the alpha price. A miner's weight is its approved work (the reward target locked when the job was assigned, not the provider bill) divided by the larger of the pool and the total work; whatever work does not claim goes to the subnet owner's hotkey and is recycled. The miner share is about 41 percent of emission: the live feed derives it from the chain's owner-cut setting, and validator v0.4.0 also accepts an explicit fixed 41 percent for new reports. So far work has been far below the pool: epochs 25840 to 25855 show about 222 dollars of approved work against about 1,420 dollars of pool (roughly 16 percent), which means most of the miner allocation goes to the owner slot by design. The docs say the reward runner rejects recipients tied to the owner's coldkey.

Recent activity

  • 2026-10-21 (#117-everyframe; everyframe-validator repo) A miner reported that validators had put all weight on the owner slot since about 18:00 UTC on 10-20 although the feed showed approved work. The team replied the same day: a missing accounting report (epoch 25836, after an RPC outage) stalled the validator, a fix was deployed (validator v0.4.0, next submission window about 13:55 UTC), and a backlog of 772 jobs worth 107.03 dollars in reward targets stays eligible. It did not call payments restored until the on-chain result is verified.

That matches the formula at the current work-to-pool ratio. It does not show whether the backlog has been paid.

Getting started

  1. Read the miner README and the mining docs first; the docs state that hosting and provider usage cost money and rewards are not guaranteed.
  2. Register a hotkey on SN117, open and fund a Phala Cloud account and at least one provider account.
  3. Install everycli from the GitHub releases, then run register-hotkey, set-api-keys, init and doctor, and deploy using the hosting quote with a maximum hourly price.
  4. Post a discount per model contract with the offer command and watch status, jobs and earnings. Check that the model IDs you serve are current: a miner reported stale IDs on 2026-10-18.
  5. Validators: use the Docker image described in the validator README. To upgrade to v0.4.1 (2026-10-21), stop the old instance and reuse the same state, wallet mounts and RPC; never clear journals.

Caveats

  • Chain weights were read on 2026-10-21 (about 20:41 UTC), but weights are validator opinions, not payouts, and with commit-reveal on they lag submissions by about two epochs. Whether the backlog of ten accounting epochs (772 jobs, about 107 dollars of approved work) has been or will be paid was not established. The code takes one report per chain epoch, and the feed adds about one report per epoch; how fast a backlog clears is not documented.
  • The team's own pages conflict: the Studio home page still says prelaunch, with renders running through existing providers, while the subnet site says live since 2026-09-28 with routing on, and also shows 0 miners online while the feed credits 4 to 10 miners per epoch. The miner README says some app traffic may bypass miners.
  • Accounting is run by the operator. Validators check signatures, not customer demand or payment, and the coordinator and the finalizer are not public. The team's docs say signed accounting is not by itself proof of customer demand.
  • The accounting feed still has a hole at epoch 25836 (404 on 2026-10-21). Validator v0.4.0 skips such gaps; earlier versions waited for the missing report.
  • Docs lag code: the rewards docs say the miner share is not hard-coded at 41 percent, validator v0.4.0 can pin 41 percent for new reports, and the live feed still uses the older chain-derived value. All three are numerically about 0.41.
  • The TEE shows which worker image ran, not that the provider executed the model; the provider, Phala's key service and the operator's review stay trusted.
  • Which of the other validator uids run the team's code is unknown. The whitepaper and roadmap files linked in chat on 2026-10-06 and 10-08 were not read, and a team update posted on 2026-10-21 at about 16:00 UTC has no readable text in the archive.
