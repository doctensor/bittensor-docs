What it is

TrajectoryRL runs a continuous competition in which miners submit packs that are tested by validators in sandboxed tasks with tests the agent cannot see. Since 2026-09-20 (Season 2, a transition season) a pack carries a fusion policy next to its SKILL.md: a program that decides which of eight open-weight models on the Engy platform answers each agent request and how their outputs are combined. One miner at a time holds the seat and receives all miner emission. The team says the seated policy will be served on Engy as an auto mode, and that it plans to turn the subnet into a host for verifiable environments later.

How it works

Miners

A miner builds a pack containing a SKILL.md and a fusion policy. The policy can be a JSON file with no code (pin a model, escalate, ask advisers), a Python file on a small SDK, or a server speaking the OpenAI chat protocol. No GPU or server is needed because validators run everything. Packs are sent with the miner CLI, which first burns a submission fee in alpha (default 50) on chain; a hotkey can submit about once every 20 minutes and can have only one pack waiting in the queue at a time. The platform keeps pack contents hidden for 24 hours. The README says a pack that earns any reward passes its copyright to trajrl.com, and all evaluation data belongs to trajrl.com.

Validators

The platform first runs pre-evaluation checks on each pack (download, format, hash, uniqueness, similarity, and an integrity judge that rejects packs whose SKILL.md carries hints matching many of the benchmark scenarios; 14 of the 131 latest listed submissions had failed a check on 2026-10-23, 13 of them at the integrity judge). A first-in-first-out queue then feeds one challenger per epoch (recently about 1.3 hours on average, at most 600 blocks). The evaluating validator runs the agent harness (Hermes) with the policy in a sidecar next to the task; a meter allows only the eight listed models, records cost and refuses a call that cannot fit in the episode's remaining 0.30 USD; a fresh verifier container then runs the scenario tests. There are 20 scenarios (terminal tasks in system administration, security, databases, scientific computing, ML systems and more, 211 tests in total); the benchmark repo publishes their tests and reference solutions, so 'hidden' means the agent never sees the verifier during a run, not that the tests are secret. Since the 2026-10-03 spec 27 change only the team's validator (UID 74, the owner's own hotkey) evaluates: the team's public API shows a single validator vote per epoch, and the other validators follow the published winner and set weights. The docs still describe stake-weighted consensus across several validators. From epoch 4420 the team says a first winning run only triggers a confirmation: two more epochs re-evaluate the seated pack and the challenger, and the takeover stands only if the challenger's 2-run average clears the usual margin and age decay; seat scores then become the 2-run average. The team puts the cost at about 10 percent more evaluation and says validators need no change.

Incentive

The score is the sum over 20 scenarios of tests passed divided by tests total, so the maximum is 20; cost is shown but not scored. A challenger takes the seat only by beating the winner by a margin of about 3 percent at low scores, shrinking to zero near the maximum, and the bar falls as the seat ages (recent takeovers cleared margins of 0.3 to 1.4 percent, and two aged seats were taken at scores 1 to 2 percent below the previous winner). The top of the scale has flattened: four different packs have scored exactly 19.9375, which is 20 minus 1/16 and fits one failed test in the one scenario that has 16 tests (an inference; the team publishes no per-test results). The seated winner gets all miner alpha: on 2026-10-23 all 8 weight-setting validators put 100 percent of their weight on the seat holder's UID (59), which received 100 percent of incentive and about 148 alpha in the last 360-block tempo (about 2,950 alpha a day at that rate). The chain's emission split was 0 percent burn, 18 percent owner, 41 percent validators and 41 percent miners (read 2026-10-21). With no valid winner, validators fall back to the owner's UID (hard-coded as UID 74 in the validator code) and miner emission aimed at it is burned.

Getting started

  1. Read the miner guide, the fusion policy guide and the benchmark page (it lists the 20 scenarios and their test counts), and install the miner CLI from the repo with pip.
  2. Write a SKILL.md and a policy (start from the examples in the repo's policy folder). Keep the SKILL.md general: the integrity check rejects packs that carry hints matching many scenarios.
  3. Build and validate the pack with the CLI, then test it with the repo's local evaluation script (scripts/eval_pack.py), which needs Docker and your own Engy API key.
  4. Check the queue on the website and the seat holder's score before paying: on 2026-10-23 about 115 packs were waiting (roughly six days) and the seat score was 19.9375 of 20. From epoch 4420 a first win also needs a two-epoch confirmation, so a takeover takes longer and needs a consistent score.
  5. Hold enough alpha for the submission fee (default 50, burned with recycle_alpha, receipt valid 24 hours and used up only when the pack enters the queue), then submit with the CLI's web-submit command and watch the status.

Caveats

  • Docs lag the platform. The website's Overview, Architecture, Consensus Score and Validator Guide pages still describe Season 1: a Qwen3.6-35B-A3B test model, several validators scoring every pack into a stake-weighted average, 150-block epochs and a winner derived locally by each validator (the Consensus Score page even gives 14 scenarios in one place and 12 in another). The Benchmark page has the 20 scenarios right but also still names the Qwen model, and the README and miner guide say 26 scenarios. Code, chat and the team API agree on spec 27, 20 scenarios, a 0.30 USD cap, 600-block epochs and one evaluating validator.
  • The dual-evaluation rule is a team announcement (2026-10-22), not yet in force at this writing. No text or code for it is in the public repo (no commit after 2026-10-04, no branch newer than 2026-09-21), although the team API already carries confirmation fields. Because validators need no change, the extra runs presumably come from the same evaluator (an inference). How the confirmation epochs interact with the queue is not published; check the winners page after epoch 4420.
  • The only evaluating validator is the owner's own hotkey, so the seat depends on one party's infrastructure; other validators copy its published winner. The scores themselves cannot be checked from the chain.
  • Spam and single-operator claims come from miners. A chain check on 2026-10-21 did not support a single operator holding the seat: 30 takeovers since 2026-10-03 went to 24 different coldkeys (none more than 3), and the first 100 queued packs came from 47 coldkeys, though the largest coldkey holds 25 of the 256 UIDs. A coldkey is not proof of one operator, and the team's own stance is that bulk submission is allowed. The team's similarity check flagged only one of 131 recently listed packs; its threshold and reference set are server-side, so it neither confirms nor refutes a miner's claim that many queued packs copy earlier winners.
  • Queue size, wait time, seat score and holder are snapshots from the team's public API on 2026-10-23 and change every epoch. The wait estimate assumes one challenger per epoch in submission order, which the API does not let anyone confirm. The queue endpoint lists only the first 100 rows; the 115 comes from the submissions endpoint.
  • The fee (default 50 alpha) is confirmed by team posts of 2026-06-23 and 2026-09-15 and by the website guide; the value the server enforces today is not public.
  • The team posted only once since 2026-10-12 (the dual-evaluation notice) and announced no change to evaluation speed, queue limits or the fee. Statements about a verifiable-environment protocol and bring-your-own-agent are plans, not built.
  • The scenario tests and reference solutions are public in the benchmark repo (last commit 2026-08-24), but the 2,800-line sandbox harness was not read line by line, nothing shows that production images carry exactly the repo's tests, and per-test results are not published, so the explanation of the 19.9375 plateau is an inference.
  • Policies run only on the eight listed models with a frozen price table; both could change between seasons.
