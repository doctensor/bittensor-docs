What it is

NeverPlayAlone is a subnet built by a two-person team that uses Minecraft as a benchmark for autonomous agents. Miners write Node.js agents that play real missions on a Minecraft server (crafting, combat and farming so far), and validators run them in sandboxes and score them. Each daily round has one winner who takes all the miner emission, and the previous winner re-enters as the champion to defend. The team says the best agents will power a paid product of hosted Minecraft worlds with AI companions. That product's early-access site is live, but it does not say that miner agents run it.

How it works

Miners

A miner packages an agent as a tar.gz with a Node entry point (index.js, built on mineflayer) and uploads it with the team's npacli tool to the team's backend while a round's submission window is open. The agent runs offline inside the validator's sandbox: no internet, read-only filesystem, and LLM calls only through a validator proxy with a small per-task spend cap (default 0.01 USD). The mission is chosen by the team and has changed over time: crafting (iron tier from 08-10, diamond tier from 08-25), combat from 09-09, and farming from 10-07 (20 minutes, four crop targets, 100 points maximum). In the benchmark code the farming score is, for each of the four crops, its points times the share of the target count held in the final inventory (capped at the target), summed and capped at 100. There is no distance factor or death penalty, and the code has only easy (20 points) and medium (30 points) tiers. A hotkey can be used in at most three rounds, and a win resets that allowance. Submissions are scanned for cheating such as movement spoofing or issuing server commands to give items, and a hit can ban the hotkey.

Validators

Validators download the frozen roster for a round from the team's API, run every entry on five task instances, and upload scoreboards. Each task's seed is a hash of the mission, the round, the chain's current block hash at the moment the task starts and the validator's hotkey, so it cannot be known before evaluation. After the scoreboard deadline each validator downloads everyone's scoreboards and computes the winner itself, averaging scores weighted by each validator's stake at the round's freeze block. The reigning champion is re-run automatically each round as the champion defense, and a challenger only takes over by beating the champion's score by the champion margin. The roster, the margin, the mission and the hotkey ban list all come from the team's closed backend. On chain on 2026-10-23, nine hotkeys hold validator permits and five had set weights, all of them putting 100 percent on the current winner. The dashboard names only two scoring validators. UID 0, which is the subnet owner's own hotkey, holds about 86 percent of the permit holders' alpha stake.

Incentive

Winner-take-all: validators put the full weight vector on the winning UID, and on 2026-10-23 the winning UID held 100 percent of the incentive. On chain the emission split is 0 burn, 0 recycle, 18 percent subnet owner, 41 percent validators and 41 percent miners, so the whole miner share goes to the winner. In the last epoch that was about 148 of 295 alpha paid to UIDs, and UID 0 (the owner's validator) received about 115 alpha of the validator share. The validator code default for burn has been 0 since 2026-07-28, after the team ran a 90 percent burn from the start of mining on 07-07, and the team said on 08-06 that subnet emission had been re-enabled. The champion margin is 1.0 point on the live dashboard feed (the docs do not give a value). The champion's code stays private until it is dethroned or has held the title for three rounds, and all other entries become public after each round. The team has listed alpha buybacks from product profits as a roadmap step, and no buyback was seen.

Getting started

  1. Read the docs site and check the current round and mission with the dashboard or the team's channel before building; the docs' round timing and mission list are out of date.
  2. Register a hotkey on subnet 98 with btcli (the registration burn was 0.1 TAO on 2026-10-23, and it varies).
  3. Clone the subnet repo and run scripts/miner_setup.sh to install the npacli submission tool.
  4. Build a Node.js agent for the active mission and test it locally with NPA-Bench, which needs Docker (see the bench repo README).
  5. Package it as a tar.gz without symlinks or absolute paths, run npacli status and npacli usage, then npacli submit while the round is open. A hotkey can enter at most three rounds.
  6. Validators need a registered hotkey with stake, OpenRouter and Chutes API keys, and a machine with 8 or more vCPUs; see docs/validator.md in the subnet repo.

Caveats

  • Chain figures are one snapshot (block 9343349, about 2026-10-23 03:00 UTC), and weights are validator opinions, not payouts. Round, champion and entrant figures come from the team's dashboard feed, which does not show coldkeys. The dashboard's own earned and burn fields are empty and were not used.
  • The team's closed backend decides who is in each round, the champion margin, the active mission and which hotkeys are banned. The repo has no copy of that backend, and validators check the ban list through the team's API before setting weights.
  • Scoring rests on one validator in practice. The owner's own hotkey (UID 0) holds about 86 percent of the permit holders' stake, and in some rounds it was the only scorer. Five validators set identical weights on chain, but the dashboard shows only two scorers, so whether the other three run the validator code or copy weights is not known.
  • The self-mining allegation is unproven and denied by the team. On chain, none of the 44 hotkeys that won a round before 2026-10-23 shares a coldkey with the owner's validator or the other validators, but that cannot reveal separate wallets the owner might control. Wins are concentrated: four coldkeys hold 49 of 76 winning entries (22 coldkeys won at least once). The 09-18 community analysis says those four are one operator reusing others' code. That was not verified and concerns a miner, not the owner.
  • The margin of 1.0 point against a 100-point maximum means a champion that scores around 99.5 is very hard to displace, yet a champion's re-run can swing widely: UID 85 scored 98.2 and then 88.8 on consecutive days. Miners say the farming seeds are too easy, the code has no hard tier, and the team had not responded to the requests in the data read.
  • The 10-22 claim that the top miner knows the next seed in advance conflicts with the seed code in the repo, which takes the block hash at evaluation time. Whether live validators run exactly that code was not checked.
  • The docs lag the live setup: they still describe 12-hour rounds, three tasks per round by default and one submission per round, and list only three missions (resource gathering, mining, crafting) with a distance multiplier the farming scorer does not use. The README still lists a 90 to 95 percent burn as a future step and says every agent is open source, but the champion's code is private for up to three rounds.
  • The chain shows this netuid was registered on 2025-04-27, over a year before the team's July 2026 launch. Who held it before, and how it reached the team, was not established.
  • The product site does not mention miners or the subnet and says its own trained agent is still under evaluation, so whether miner agents power the paid product is unconfirmed. Team claims of a commercial path and alpha buybacks were not backed by anything seen.
  • A miner banned on 08-22 asked whether forking a published agent is allowed, and no answer was found. Neither repo has a license file or tagged releases, and validators can auto-update from the main branch.
  • In the validator code the fallback that reuses the last saved winner does not re-check that its UID still belongs to the same hotkey. This is a reading of the code, not a seen incident: the 10-20 hotkey change was followed correctly on chain.
