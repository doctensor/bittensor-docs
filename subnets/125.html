What it is

Refinery (SN125) pays for research that improves how open language models are trained. Challenge 1 asks for optimizers that reach lower validation loss than the current best under a fixed compute budget; Challenge 2, open since 2026-10-19, asks for a refiner that decides what a fixed student model reads and which tokens get gradient. One team-run validator trains every submission itself and publishes the winning source and per-round records. On 2026-10-23 the chain pays three miner UIDs, one per confirmed improvement holder, and routes the unearned share to the owner slot, which is set to burn it.

How it works

Miners

Miners write an optimizer (or, for Challenge 2, a refiner) in Python using the repo's interface, test it on their own compute, serve the source from a registered hotkey and prepay evaluation credits in TAO. They commit to the source hash first and reveal the code when asked; a commit with no credit behind it is rejected. One hotkey carries one submission at a time. A GPU is not needed just to serve code, but real experiments need one.

Validators

One validator, pinned in the repo config (UID 203), trains each submission on a fixed task: a roughly 360M-parameter Llama-style model on FineWeb-Edu for at most 20 hours on one B200 (188,000 steps), on rented GPUs (the dashboard lists RunPod). Miners refuse queries from any other hotkey. Optimizers are scored on held-out validation loss and refiners on a benchmark suite. A candidate must clear a bar and then pass a second, validator-funded confirmation run before it counts. Rounds are scheduled on a daily 00:00 UTC grid, although overruns shift the start. On chain, all 11 validators that set weights on 2026-10-23 carried exactly the same vector as that validator, which holds about 1 percent of validator stake. Anyone can recompute weights from the published round records, but the training run itself cannot be replayed bit for bit.

Incentive

Miners get 41 percent of subnet emission on chain (owner 18, validators 41), and half of that backs each challenge pool. A pool pays only as far as recent confirmed progress covers a reference level: each confirmed improvement counts with a 14-day half-life, and the reference ramps up over 56 days from the first confirmed event (optimizer 0.03 to 0.10 nats, refiner 0.02 to 0.07 suite points). A new event must beat the best by 0.03 nats (optimizer) or 0.02 suite points (refiner) and by an adaptive amount that halves each stagnant week. The unearned share is weighted to UID 0, the owner slot, and the subnet's RecycleOrBurn setting is Burn. On 2026-10-23 the optimizer pool was 48 percent payable (confirmed events on 2026-09-11 and 2026-10-06, split 64 to 36) and the refiner pool 100 percent payable (one event on 2026-10-21), so the chain vector read 50.0 percent to the refiner leader, 15.4 and 8.6 percent to the two optimizer holders and 26.0 percent to the owner slot. With no new optimizer event the same formula pays out less each day: about 19 percent of that pool by 2026-11-06, by my calculation from the published constants.

Getting started

  1. Use Linux and Python 3.12, install the repo requirements and read MINING.md (and MINING_AGENTS.MD if you use research agents).
  2. Start from the optimizer template or the refiner template (docs/REFINER_MINING.md) and check your candidate locally without executing untrusted code.
  3. Run isolated experiments against the published baseline before paying anything.
  4. Check the dashboard and the signed round announcement for the current fee (0.85 TAO on 2026-10-23), the treasury address and the validator identity, then register a hotkey and fund evaluation credits.
  5. Serve your source, commit its hash and reveal it when the round asks.

Caveats

  • Dashboard figures (alpha paid, rental spend, submission counts) are published by the team and were not checked independently; the weight vector in it matches the chain to 0.01 point. The repo itself warns that a source release is not proof of an active deployment and tells miners to check identity, treasury and fee against a signed round announcement before paying.
  • All 11 validators that set weights on 2026-10-23 carry the same vector as the team's validator, which holds about 1 percent of validator stake. The public repo has no code for the other validators (a config comment mentions a lite attestation validator), so how they obtain the vector is not documented here.
  • Challenge 2 is scored on a benchmark suite that its own spec calls a placeholder, and the held-out loss gate is switched off: all seven refiner results so far have a worse held-out loss than the baseline (2.86 to 3.24 against 2.59 nats) while scoring 0.04 to 0.06 higher on the suite, and the LAMBADA sub-score fell below the baseline in the two results inspected.
  • Fees are prepaid in TAO (0.85 TAO on 2026-10-23, up from about 0.72 at launch). TAO is never refunded, but an evaluation credit is refunded when the evaluation fails on the validator's side; a credit is lost on miner fault or an unrevealed commit.
  • Participation is thin and falling: accepted submissions per round went 5, 3, 2, 0 after Challenge 2 opened. Only three miner UIDs are paid on chain, on three different coldkeys, none shared with the owner slot or the treasury address; that fits the team's statement that it has no miner of its own, though the chain cannot rule out other wallets. Most of the chat is GIF spam.
  • The team's planned six-week review (about 2026-10-20) has no recorded outcome beyond the 2026-10-19 announcement, and the code has no scheduled pause. The announced cut is not a code change: the payout formula already shrinks the optimizer share as old improvements decay.
  • One README paragraph still calls data selection a future direction while another describes Challenge 2 as open since 2026-10-19. The repo has no LICENSE file and has not changed since 2026-10-17.
